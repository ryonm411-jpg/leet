Online assessment checklist

For the Amazon SDE Intern OA. Sources: your recruiter email, and Amazon's OA prep page and video transcripts, read on 2026-11-08. Where they disagree, your invitation email wins.

Prepare for both: two problems in 70 minutes (about 35 minutes each) and the repository task. The feedback survey is required. Amazon says your OA isn't finalised until it's done.

Amazon's official rules

  • Allowed: "publicly accessible online resources", meaning language docs such as docs.python.org. Not allowed: sites that need a login, and private repos. "Your browser usage is logged."
  • Don't use Print Screen. Amazon says the session is terminated and you're locked out.
  • Don't copy and paste code in. "We expect this to be your own code." AI tools are out too.
  • "If you get stuck on a problem, move to the next one and revisit."
  • Use a laptop or desktop, not a phone or tablet. The platform is HackerRank, which you can try on the practice test.

What they grade (Amazon's video)

Reading the problem deeply, turning the idea into code accurately, choosing the right data structure (list, map or set), common-sense runtime complexity, and a simple solution. They say they don't set trick questions.

Before the day

  • Find the exact deadline in the "SDE-I Online Assessment Invitation" email, and plan to finish at least a day early.
  • Take the HackerRank practice test, so the editor is familiar before the timer starts.
  • Read the Leadership Principles.
  • Block 2.5 hours somewhere quiet, with a stable connection. The coding timer can't be paused.
  • No AI, no notes and none of this workspace during the test. Public language docs are the only outside help allowed.

Coding problem

StepDo
1Read it one paragraph at a time, as Amazon's video does, and list every requirement. Use the example to decode the output format. Write two examples, including an edge case: one item, all equal, or the answer at the very end.
2Name the pattern: seen map, frequency count, two pointers or sliding window. If none fits, say the brute force.
3If no faster idea comes within about 10 minutes, code the brute force. A working answer beats an unfinished one.
4Trace one example by hand, then run.
5With time left, make it faster. Keep the working version in a comment.

Repository question

  1. Read the task and the README. Know what "done" means.
  2. Run the tests before changing anything.
  3. Read the failing test. It gives you the input, the expected result and what actually happened.
  4. Follow the calls with F12, Go to Definition. The bug is where a value first goes wrong, which is often not in the file the test names.
  5. Set a breakpoint, Debug Test, and look at the real values.
  6. Make the smallest change, then run every test. Never edit a test to make it pass.

Work Style Assessment

It explores how you approach work and make decisions. Third-party guides say it uses pairs of statements, which is unconfirmed. Answer honestly and consistently. Guessing what Amazon "wants" tends to make your answers contradict each other.
