A working answer first

Amazon doesn't publish how the OA is scored. Third-party guides say the coding answer is checked against test cases, some of them hidden, but that isn't confirmed. Either way, the safest plan is the same:

  1. Read twice, then write two examples, including an edge case: one item, all equal, the answer at the very end.
  2. Say the brute force. It's the direct approach that tries every possibility (see the glossary).
  3. If no faster idea comes within about 10 minutes, code the brute force. A correct slow answer passes the small tests. An unfinished fast one passes none.
  4. Trace one example by hand, then run.
  5. With time left, make it faster. Keep the working version in a comment so you can go back to it.

This follows the Tech Interview Handbook's coding interview techniques. Your full OA-day list is in the OA checklist.

You're 12 minutes in. You can see an O(n·k) answer but not an O(n) one. What now?

Timed problem: Quietest Shift

Start the timer before you read on. When it runs out, stop, as you would in the real test. Two tests are visible. The other six are hidden, as in the OA, so you'll only see pass or fail.

A warehouse logs how many orders arrive each hour. loads[i] is the count for hour i. Maintenance needs k hours in a row, and should go where the total load is smallest.

Return the starting hour of the k-hour stretch with the smallest total. If several stretches tie, return the earliest. You can assume 1 ≤ k ≤ len(loads) and that every count is 0 or more. One hidden test is large, so O(n) passes it and an approach that re-adds every stretch is too slow.

Example: loads = [5, 2, 1, 4, 3, 1], k = 2. The stretches total 7, 3, 5, 7 and 4, so the answer is 1.

Stuck for 15 minutes? Show a hint, not a solution

This is Lesson 9's window again, with two changes. You track the smallest total, not the largest. And you store where it started, not the total. Which index starts the window whose newest item is i? Think about which comparison keeps the earliest of a tie.
