Design a link shortener, in four steps

About 45 minutes · Quizzes, two estimates, one Python class, one worksheet · Your win: you can lead the first five minutes of a design question and build its core in Python

A design question has no single right answer, and that's what makes it feel scary. But it does have a shape, and the shape can be learned. This lesson teaches the shape on the classic first question, "Design bit.ly", and then has you build its heart in Python. That heart turns out to be two hash maps, which you already know.

Part 1: the four steps

The most widely used free guide, the System Design Primer, opens with: "The system design interview is an open-ended conversation. You are expected to lead it." It gives four steps:

  1. Outline use cases, constraints, and assumptions. Ask what it must do, for whom, and how much traffic it gets. Say out loud what you're leaving out.
  2. Create a high level design. The main boxes (client, server, database) and the arrows between them.
  3. Design core components. Zoom into the most important part: here, how a long URL becomes a short code and back.
  4. Scale the design. Find what breaks when traffic grows, and fix that one thing.

The interviewer says "Design bit.ly." What do you do first?

Part 2: Step 1, scope and numbers

The Primer's worked answer to this question (its Pastebin / Bit.ly solution) scopes it to: a user submits something and "gets a randomly generated link"; a user enters a link and views the contents; users are anonymous; links can expire; and the service tracks visit analytics. It puts these out of scope: accounts and login, editing, and choosing your own link. Then it assumes numbers: 10 million new links a month, 100 million reads a month, a 10:1 read-to-write ratio.

Next comes a back-of-the-envelope estimate. The Primer's shortcut is that a month has about 2.5 million seconds. Divide by that to turn "per month" into "per second". Type your answers.

Reads outnumber writes 10 to 1, and a few links go viral. What helps most?

Part 3: Steps 2 and 3, the boxes and the core

Client ──► Web server ──► Write API ──► Database  (short code → long URL)
                    └───► Read API ──► Cache ──► Database

That's roughly the Primer's high-level design: a web server in front, separate write and read paths, and a store that maps each short code to its content. The core is a key-value lookup: given a code, find the URL. In memory that's a Python dict. At scale it's a database table with the code as its indexed key, or a key-value store.

Making the code. The Primer hashes the input with MD5, then uses Base 62, the characters [a-zA-Z0-9], and takes the first 7 characters, giving 627 (about 3.5 trillion) possible codes. It checks the database for a clash and regenerates if one exists. A simpler approach that interviewers also accept: give each new URL the next number, 1, 2, 3, …, and write that number in base 62. No clashes are possible, but codes become guessable. That's a trade-off worth saying out loud.

Why Base 62 and not Base 64, which packs in more per character?

Part 4: build the core (object-oriented design, in Python)

Some interviews, especially for new grads, ask you to code the heart of a design as a class. Build Shortener with the counter-and-base-62 approach:

  • shorten(url): if this URL was shortened before, return the same code. Otherwise give it the next number (the first URL gets 1) and return that number in base 62, using ALPHABET, where "0" is 0, "a" is 10 and "Z" is 61.
  • expand(code): return the original URL, or None if the code was never handed out.

Python classes, for Java habits: there are no field declarations, so set fields in __init__ as self.name = .... Every method takes self first, and you write self. every time you use a field (Python tutorial, classes). No this, no new. The tests call run_ops, which is already written. Leave it as it is.

Three fields in __init__: self.next_id = 1, self.code_of = {} (url → code) and self.url_of = {} (code → url). Two dicts, one for each direction: the seen map, twice. In shorten, check url in self.code_of first. For base 62, n, r = divmod(n, 62) in a loop, adding ALPHABET[r] to the front of the code. expand is a single .get.
